# ADR-001：统一插件平台与宿主能力适配

日期：2026-11-03。状态：已采纳；用户已授权按完整架构实施，内部市场与 Agent 为首批接入。

## 背景

EOS Agent 已有 `plugin.toml + MCP/Skills` 安装路径，服务端另有 `plugin.json + Web 页面` 插件路径。用户说明目前没有正式插件，因此应在生态形成前建立完整统一架构，降低之后各产品重复实现和插件迁移成本。

## 决策

1. 统一市场、身份、发布、授权、生命周期和宿主协议；以能力版本协商连接不同应用。
2. `publisher.slug` 是永久 ID；应用适用范围与 ID 分离，`portable/targeted` 显式声明。
3. 统一根清单选用 `plugin.toml`，标准解析加 Schema 校验；`.eos-plugin` 使用 tar.gz。发布元数据独立签名，包以摘要寻址。
4. 共享契约与运行模块由 `eos-plugins` 工作区拥有；市场通用业务在 base，EOS 应用及策略在 pro，应用只实现适配器。依赖单向。
5. UI 采用隔离页面和消息协议；共享 SDK 不注入宿主 React/Vue/Solid 等实例，也不给通用插件原始登录 HTTP 客户端。
6. Skills、MCP、WASM 与 UI 是不同执行器；本机受信进程的权限边界必须如实表达。没有已验证隔离能力时拒绝 `sandboxed-process`。
7. 初期市场嵌入现有服务部署；托管执行工作进程与账号/支付服务隔离。通用模块可后续拆服务，不提前增加部署拓扑。
8. 固定目标版本、制品、计划摘要与授权；更新元数据采用成熟 TUF 模型。用显式迁移转换旧格式，运行时不保留双格式或旧实现回退。

## 选项与权衡

- **每个应用各建市场**：短期界面实现方便，但身份、权限、发布和 SDK 必然分叉，不能满足 EOS 系列统一接入，放弃。
- **直接把后台 JS 插件用于所有产品**：绑定现有框架和页面全局权限，桌面、服务端和无 UI 能力难以接入，放弃。
- **只把 MCP 当成插件规范**：可复用工具连接，但不能完整表达 UI、分发、升级事务、包信任和宿主业务权限，作为执行器保留。
- **只增加适用应用字符串**：无法判断能力版本、执行位置、真实隔离和授权范围，不足以作为完整方案。
- **统一 JSON 根清单**：服务端已有可复用模型，Schema 工具直接；但 Agent 已用 TOML。两者都可行，本提案选标准 TOML 转对象校验来保留现有开发习惯，不保留手写宽松解析器。
- **让任何原生插件都声称细粒度沙箱**：普通子进程能绕过代理访问系统，声明不等于执行限制，放弃。

## 影响

- Agent 的插件管理路径需要改造，但 MCP/Skills 核心能力继续复用。
- 后台插件模板、加载器和注册方式需要迁入同一合同；已有管理能力可复用，不能把旧格式一直带到新平台。
- 需要共享 SDK/协议发布与符合性测试，宿主集成成本转为有边界、可重复的适配成本。
- 不保证未来所有宿主都具备相同执行能力；平台负责精确解释支持与拒绝原因。
- 首期实现范围必须覆盖安全、事务和第二宿主合同验证；“内部使用”不作为跳过这些约束的理由。

替代本决策需新增 ADR，明确 Schema/API 版本、迁移和原有发布信任的处理方式。
